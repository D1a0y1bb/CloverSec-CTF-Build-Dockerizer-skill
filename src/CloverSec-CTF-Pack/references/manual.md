# 题目手册写法

手册是交付物里最重要的一份文件。它同时给三种人看：当场的值守运维、赛后复盘的人、以及以后要改这道题的人。写浅了这三种人都用不了。

`README/<题目类型-题目名称>.md`，文件名和交付目录同名，一个字都不能少、不能改。截图放同目录的 `assets/`，正文用相对路径引用：`![截图](assets/image-20261007112926.png)`。

## 硬性要求

写之前先记住这五条，违反任何一条都要重写：

1. **文件名必须是 `<题目类型-题目名称>.md`**。`Web-Shiro-Heapdump` 题就写 `README/Web-Shiro-Heapdump.md`。不要写 `shiro-heapdump.md`、`题目手册.md`、`README.md`、`手册.md`。类型取交付目录名前缀那 20 个之一。
2. **1.2 题目描述只写氛围和悬念，不能泄漏任何解法**。不出现技术栈版本、漏洞类型名、文件路径、函数名、参数名、端口以外的东西，也不能写「选手需要读取 Actuator heapdump」这种把解题路径说出来句子。技术内容全部放到 1.4 考察信息和 1.9 解题步骤。
3. **1.9 解题步骤要能被人照着复现**。写真实命令、真实 payload、真实响应，不写「连接服务」「按常规方法利用」这类占位。参照题解手册的详细度：一条链涉及几步就分几节写，每节给命令、给预期输出、给关键截图位置。
4. **1.5 旗帜信息和 1.7 部署方式按下面的清单逐项写全**，不能只写一句话。这两节是值守和平台运维最常翻的两节。
5. **不写「常见失败现象」这一节**。排障过程属于出题人自己的工作记录，不属于交付手册。

## 章节骨架

编号和层级照抄，顺序不能变。纯附件题去掉 1.7，编号顺延。

### 1.2 题目描述

### 1.5 旗帜信息

### 1.6 题目情况

### 1.7 部署方式

### 1.8 题目设计

### 1.9 解题步骤
```

### 1.1 题目名称

题目在平台上显示的完整名称，和交付目录、镜像名保持一致。

```markdown
### 1.1 题目名称

Web-残影
```

### 1.2 题目描述

一到三句，写出场景、悬念和一点点幽默感。这是选手在平台上唯一看到的一段文字，风格参考出题人的原话：

```markdown
### 1.2 题目描述

凌晨三点，图片审核台收到了一张"只存在一瞬"的 GIF。你能在这道残影彻底消失前抓住它吗？
```

```markdown
### 1.2 题目描述

额滴神，url 后面怎么有个 `?url=`，难道是我眼花了？我觉得这是一道送分题，首先我不会告诉你这是什么漏洞，好好的试着修复一下，或许能绕过出题人的 check 呢？
```

写的时候注意：

- 口语化和自嘲都行，别端着，但不要写成段子集。
- 可以暗示题目的"感觉"（转瞬即逝、藏了个东西、看起来很平凡），不能暗示漏洞类别。
- 一句话以内讲完，不要解释背景设定。
- 不能出现这些词：反序列化、注入、绕过、heapdump、gadget、弱类型、SSRF、SSTI，以及任何 CVE 编号、函数名、文件名、类名。

### 1.3 题目难度

简单 / 简单到中等 / 中等 / 中高难度 / 困难，五个档位选一个。

### 1.4 考察信息

这里才写技术内容。列出这道题实际考察的知识点，用顿号或分号连成一行，或者一行一个：

```markdown
### 1.4 考察信息

Nginx location 匹配优先级、PHP-FPM 路径截断、文件上传 TOCTOU 竞态、pcntl 绕过 disable_functions
```

难度说明要跟 1.8 的实际链路对上，不要写大于实际考察面的范围。

### 1.5 旗帜信息

逐项写清下面这些，能确定的都写上，不确定的写"运行时确认"，不要空着：

- Flag 文件位置，写容器内的绝对路径。
- 权限和属主，例如 `444`、`root:ctf 440`。
- 谁在什么时候读它：是每次请求读文件，还是启动时读进内存，还是从数据库读。这一条决定平台换 Flag 会不会生效。
- 平台覆盖方式：平台执行的那条写入命令，写全。
- 如果程序读的不是 `flag.path`（软链接、包装文件、配置载入、数据库），把接法写清楚，并说明为什么必须这样接。
- 旧平台通过环境变量传值时，写清变量名和处理位置。

```markdown
### 1.5 旗帜信息

动态 Flag，平台启动后覆盖。

- Flag 文件：`/flag`
- 权限：`444`，属主 `root:root`
- 读取方式：每次请求 `file_get_contents('/flag')`，平台换 Flag 立即可生效，不需要重启
- 平台覆盖命令：

  ```bash
  docker exec <容器> sh -c 'printf "%s\n" "$1" > "$2"' sh "$new_flag" /flag
  ```

- 无软链接、无包装脚本，程序直接读 `/flag`。
```

```markdown
### 1.5 旗帜信息

原始静态 Flag 为占位值 `flag{placeholder}`，平台启动后覆盖。

- Flag 文件：`/home/ctf/flag`
- 权限：`440`，属主 `root:ctf`。题目进程以 `ctf` 运行，能读不能改
- 读取方式：`win` 函数每次被调用时 `fopen("/home/ctf/flag")`，不缓存
- 平台覆盖命令：

  ```bash
  docker exec <容器> sh -c 'printf "%s\n" "$1" > "$2"' sh "$new_flag" /home/ctf/flag
  ```

  注意写入后属主会变成 `root:root`、权限按 umask 给出。平台要求的是程序可读，本步骤不影响读取；如果题目对权限有硬性要求，在手册里注明需要补一次 `chown root:ctf /home/ctf/flag && chmod 440`。
```

数据库或配置文件里的 Flag，还要给出平台要执行的完整命令：

```markdown
### 1.5 旗帜信息

Flag 存在数据库表 `flag_tab` 里，程序每次查询读取。

- 平台覆盖命令：

  ```bash
  docker exec <容器> mysql -uroot -proot -e "USE ctf; UPDATE flag_tab SET flag='$new_flag' WHERE id=1;"
  ```

- 容器内 start.sh 每秒比对一次 `/flag` 与库内值，不一致就同步。平台先写 `/flag` 再执行上面的命令，两种方式都能生效。
```

### 1.6 题目情况

这一节写"这道题跑起来是什么样"：监听哪些端口、有哪些服务、初始账号密码、后台地址、判题脚本在哪、有没有 ttyd、有没有依赖的数据库或外部服务。用列表写，一行一件事。

```markdown
### 1.6 题目情况

容器同时运行 Apache、PHP 5.6、MariaDB 和 ttyd。

- Web 端口：`80`
- ttyd 端口：`8022`，账号 `ctf/123456`
- 后台地址：`/admin506/`，初始账号 `admin/admin`
- 数据库：容器内 MariaDB，首次启动导入 `src/docker/init_zzzcms.sql`
- 正式判题脚本：`check/check.sh`（RDG 题）
```

### 1.7 部署方式

**这一节是硬性清单，八项都要有。** 命令必须能直接复制执行，不能出现 `<按实际情况填写>` 之外的占位符。

1. 目录说明：`src/`、`solve/`、`附件/`、`镜像/`、RDG 题的 `check/` 各是什么，一句话一个。
2. 构建镜像的命令，带 `--platform linux/amd64` 和镜像名。
3. 交付 `镜像/` 目录时，写出镜像 tar 的路径和 `docker load -i` 导入命令；没交付就明说用构建。
4. 启动命令：**`docker run` 最后必须显式带上 `/start.sh`**。平台就是用 `/start.sh` 覆盖 `CMD` 启动容器的，手册里的命令要跟平台一致。带 `-d --name`、完整端口映射、需要的环境变量。
5. 访问地址：Web、ttyd、后台入口分别列出来。
6. 平台写入 Flag 的命令，和 1.5 一致。
7. 停止和清理容器的命令。
8. 端口按现场环境调整时，说明改完端口后 check 和手册里的命令同步改哪里。

```markdown
### 1.7 部署方式

在本目录执行：

```bash
docker build --platform linux/amd64 -t web-afterimage:latest .
```

交付了镜像 tar 时改用：

```bash
docker load -i 镜像/web-afterimage.tar
```

启动容器，注意 `/start.sh` 是平台入口，必须显式带上：

```bash
docker run -d --name web-afterimage \
  -p 8080:80 \
  web-afterimage:latest /start.sh
```

访问地址：

- Web：`http://127.0.0.1:8080/`
- 后台上传入口：`http://127.0.0.1:8080/admin/upload.php`

平台启动后写入 Flag：

```bash
docker exec web-afterimage sh -c 'printf "%s\n" "$1" > "$2"' sh 'flag{example}' /flag
```

停止并清理：

```bash
docker rm -f web-afterimage
```
```

端口可以按现场环境调整时，在命令下面补一句说明，例如「平台把容器 `80` 映射到 `31001` 时，判题脚本用 `31001`」。

旧平台用 `changeflag.sh` 的题，把这一段也写进来：

```markdown
容器内保留了旧平台的 `/changeflag.sh`，平台通过 `FLAG` 环境变量传值时由它写入：

```bash
docker run -d --name web-afterimage -p 8080:80 -e FLAG='flag{example}' web-afterimage:latest /start.sh
```
```

### 1.8 题目设计

写这道题是怎么设计的、漏洞点在哪、为什么这么设计。守方和后续改题的人靠这一节理解题目意图。分点写，涉及代码的贴关键片段。

```markdown
### 1.8 题目设计

1. 选手上传一个 GIF，服务在两秒后删除；
2. 删除前 Nginx 已经把请求交给 PHP-FPM，形成约 300 毫秒的竞态窗口；
3. 竞态命中时文件已被删除但 `pcntl` 子进程仍持有句柄，可以读到内容。

`src/upload.php` 里删除逻辑写成"入队 + 定时清理"而不是同步 unlink，就是为了留出这个窗口。
```

补全题、迁移题在这一节写清和原题的关系：原资料缺了什么、补了什么、哪些部分没有恢复。这块内容也可以单独起 `1.10 真实性边界`，但不要省略。

### 1.9 解题步骤

**这一节决定手册能不能用，必须写到别人照着能复现的程度。**

- 按真实攻击顺序分步，一步一小节，编号 `1.9.1`、`1.9.2`……没有多步时就用自然段加代码块。
- 每一步给**可直接复制的命令或完整 HTTP 报文**，给**预期输出**，必要时指明截图位置。
- payload 要写真的，不要写 `payload_here`、`<你的利用脚本>`。自己的利用脚本贴进正文或放进 `assets/`。
- 涉及数据库、文件路径、账号密码的，把实际值写出来（平台 Flag 除外）。
- 最后一步要落到"拿到 Flag"，并说明 Flag 长什么样。

```markdown
### 1.9 解题步骤

#### 1.9.1 确认目标可达

```bash
curl -i http://127.0.0.1:8080/
```

预期返回 `HTTP/1.1 200`，页面标题为 `图片审核台`。

#### 1.9.2 摸清上传接口

上传入口在 `/admin/upload.php`，只接受 `image/gif`：

```bash
curl -i -F 'file=@test.gif;type=image/gif' http://127.0.0.1:8080/admin/upload.php
```

预期返回：

```text
{"ok":true,"id":"2f3a..."}
```

#### 1.9.3 打竞态窗口

服务在 2 秒后删除文件，删除前已经交给 PHP-FPM。用一个循环持续请求刚上传的文件 ID：

```bash
for i in $(seq 1 400); do
  curl -s "http://127.0.0.1:8080/preview.php?id=2f3a..." -o /tmp/out &
done
wait
grep -ao 'flag{[^}]*}' /tmp/out
```

命中窗口时 `/tmp/out` 里会带出完整的 GIF 内容，其中包含：

```text
flag{...}
```

截图位置：`assets/image-20261007112926.png`
```

## 附件题的手册

同样是上面的骨架，去掉 1.7 部署方式，编号顺延（原 1.8 变 1.7，1.9 变 1.8）。改两点：

- 1.6 题目情况写清发了哪些附件、每个附件是什么、选手需要什么环境打开。
- 解题步骤末尾写清解到的是什么（一段明文、一个 Flag、一个文件），以及是否需要联网。

## RDG 题的手册

RDG 是防守加固赛制，手册的读者比普通题多一类：现场要判断"选手到底修好没有"的人。骨架同上，另外做这几件事：

- 1.5 旗帜信息里说明这道题的 Flag 是**动态写入**还是**固定值设计的一部分**。有些 RDG 题的敏感目标就是自己配置里的固定内容，不从 `/flag` 读，这种情况要明确写出来，别让人以为平台写 Flag 没生效。
- 1.6 题目情况里列出 ttyd 端口和账号、后台地址和账号、`check/check.sh` 的位置。RDG 题必须保留 ttyd，选手要能进容器改代码。
- 1.8 题目设计里逐条列出 check 覆盖的关卡，以及每关在**未加固**和**已加固**状态下的预期结果。
- 1.9 解题步骤改成"初始漏洞验证 + 修复方法"两段：

```markdown
### 1.9 初始漏洞验证与修复方法

#### 1.9.1 初始漏洞验证

未加固时漏洞应当可复现：

```bash
curl 'http://127.0.0.1:8080/html/index.php?url=file:///etc/passwd'
```

预期返回：

```text
root:x:0:0:root:/root:/bin/bash
```

#### 1.9.2 修复方法

进入容器（ttyd 或 `docker exec`）：

```bash
docker exec -it sjq-rdg-hospital-appointment-miniapp /bin/bash
```

修改 `/var/www/html/html/index.php`，只允许 `http://` 和 `https://`：

```php
<?php
$url = $_GET['url'] ?? '';
if (!preg_match('/^https?:\/\//i', $url)) {
    http_response_code(400);
    die('Invalid URL. URL must start with http:// or https://');
}
// 省略：按原逻辑请求并输出
```

修复要点分点列出，说明为什么这样改能过 check（例如「PHP 请求不能因为修复代码报 5xx，否则 check 判定不通过」）。

#### 1.9.3 加固后自检

```bash
./check/check.sh 127.0.0.1 8080
```

初始环境预期：

```text
检测点3: file:///etc/passwd 仍可被读取，SSRF 未修复，测试不通过
ok: False
```

加固后预期：

```text
检测点3: file 协议读取已被拦截，SSRF 修复验证通过
ok: True
```
```

## 语言和格式

- 一句话说清一件事。不写"本题目旨在……"、"值得注意的是"这类铺垫。
- 不用加粗堆重点，不用 emoji，不写形容词式的评价（"优雅的绕过"）。
- 命令块标明语言：`bash`、`http`、`php`、`python`、`text`。
- 截图和流程图放进 `README/assets/`，正文里用相对路径引用，不要贴外链图床地址。
